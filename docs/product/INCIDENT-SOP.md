# 线上故障响应 SOP

本文定义 Debussy 内部运行异常从发现、分级、止损、恢复到复盘的标准流程。正式响应时限和值班安排待确认；当前不提供对外 SLA。

当前适用于团队日常使用的内部环境。首要恢复目标是文本 Agent 主链路；实时语音和数字人异常默认可降级，不升级为文本版本的整体不可用，除非同时影响核心链路或数据安全。

当前内部环境运行在开发机上，没有独立高可用节点。当前机器和本地备份可用时，允许暂停服务并从已验证备份恢复；迁移至局域网服务器后需要重新评估分级、访问控制和恢复目标。

进入内部日常使用后的恢复点目标（RPO）为 24 小时：每天自动备份，保留最近 14 天。当前尚未启用自动备份，不具备该保证。启用后若最近成功备份距当前超过 24 小时，按 P1 数据恢复风险处理；若同时发生数据损坏且无可用恢复点，升级为 P0。

进入内部日常使用后的恢复时间目标（RTO）为 4 小时，从决定执行恢复到文本 Agent 主链路验证通过。该目标仅适用于当前机器和本地备份仍可使用的情况，须在首次恢复演练通过后生效。当前阶段已接受不做异机或异地备份的风险；机器或同一存储介质损坏时无法承诺恢复点和恢复时间。

## 目标

- 优先保护用户、租户隔离、数据和凭据安全。
- 尽快恢复核心文本对话与发布可控能力。
- 保留清晰时间线和证据，不在处置过程中扩大影响。
- 将事故结论转化为测试、监控、产品或流程改进。

## 事件分级

| 级别 | 判定 | 典型示例 | 默认动作 |
| --- | --- | --- | --- |
| P0 严重 | 安全/隔离失效、数据损坏、核心服务大范围不可用或影响持续扩大 | 跨 Tenant 数据访问、凭据泄漏、发布版本不可控、数据库不可恢复写入 | 立即停止相关发布和变更，成立事件响应，止损/回滚 |
| P1 高 | 主要用户链路显著受损，无可靠替代路径 | 大量对话失败、Embed 无法建连、发布或回滚不可用 | 快速响应，降级或回滚，持续通报 |
| P2 中 | 局部功能受损，有明确替代路径 | 单一 Provider、语音或附件能力异常，文本主链路可用 | 指定负责人，限制影响并计划修复 |
| P3 低 | 轻微体验、展示或低频边缘问题 | 非关键样式、文案或少量可重试错误 | 进入常规缺陷队列 |

若无法判断是否涉及安全、数据或跨租户影响，先按更高级别处理。

## 角色

- 事件指挥：确定优先级、分配任务、决定降级/回滚并控制变更。
- 技术处置：定位组件、实施止损和恢复。
- 记录员：维护时间线、证据、决策和行动项。
- 沟通负责人：向内部和受影响用户同步已确认事实。
- 安全/数据负责人：处理凭据、隔离、数据完整性和合规事项。

当前由产品负责人承担事件升级、恢复确认和发布解冻的最终决策。技术处置、记录和沟通可由其指定团队成员执行；正式值班表、联系方式和替补机制待确认。

## 响应流程

### 1. 发现与登记

记录：

- 首次发现时间和发现渠道。
- 环境、Tenant、Agent、应用、Revision/App Version 和来源。
- 用户可见症状、错误码、请求/事件关联 ID。
- 最近发布、配置、迁移和 Provider 变化。
- 已确认事实与尚未验证的假设。

禁止在事件记录中粘贴令牌、密钥、完整用户文本或敏感附件。

### 2. 分级与建立指挥

1. 评估安全、数据完整性、影响用户数、影响范围和是否存在替代路径。
2. 指定唯一事件指挥和记录位置。
3. P0/P1 冻结无关发布和配置变更。
4. 设定下一次状态更新时间；响应时限待确认。

### 3. 止损

按最小影响原则选择：

- 暂停受影响 Published App 或阻止新流量。
- 回滚到已验证的 App Version/服务版本。
- 关闭语音、附件或单一 Provider，保留文本对话。
- 降低并发、限制来源或启用既定限流。
- 隔离受影响 Tenant，不扩大到其他租户。
- 涉及凭据时吊销并轮换；不得只删除日志而继续使用旧凭据。

任何不可逆数据操作必须由事件指挥和数据负责人确认，并先保留恢复证据。

### 4. 定位

优先按稳定边界缩小范围：

- 客户端：管理员入口、Embed 入口、浏览器、网络和版本缓存。
- Control Plane：Tenant、Agent、发布、Usage 和管理员会话。
- Data Plane：bootstrap、exchange、Conversation、附件和终端身份。
- Runtime Plane：会话执行、工具、模型 Provider 和流式事件。
- 基础设施：PostgreSQL、Redis、网络、磁盘和时间同步。
- Voice：服务健康、模型加载、CUDA、并发、首包和流取消。

使用安全错误码、指标和关联 ID 定位；不要为排障临时记录完整输入内容或凭据。

### 5. 恢复与验证

恢复后必须验证：

- 受影响主链路重新可用。
- Tenant、版本和身份范围正确。
- 数据完整性及迁移状态明确。
- 错误率、延迟、连接和资源指标恢复到基线。
- 降级开关、暂停状态和临时限流的后续处理已登记。
- 原故障可以通过监控或验证步骤明确识别为已恢复。

当前单机恢复顺序为：先确认开发机和 Docker 可用，再恢复 PostgreSQL 与 `runtimes/pi/.pi/admin-dev/` 中的身份材料，随后启动服务并执行文本主链路冒烟。Redis 为短期状态，可清空后通过重新连接建立；不得把 Redis 恢复作为 PostgreSQL 数据恢复的替代。

恢复时选择事故发生前最近的已验证备份，记录恢复点时间和预计数据缺口。恢复完成后核对 Tenant、Agent、Revision、Published App、App Version、Usage 和 Session 数据，并确认身份材料与数据库中的对象关系一致。

恢复不等于事件关闭；仍需完成观察和复盘。

### 6. 沟通

每次通报只包含已确认内容：

```text
事件级别与状态：调查中 / 已止损 / 恢复观察 / 已关闭
开始时间：
影响范围：
用户表现：
已采取措施：
当前替代方案：
下一次更新时间：
```

不得猜测根因或承诺未验证的恢复时间。

### 7. 关闭与复盘

关闭条件：

- 用户主链路和关键指标在确认后的观察窗口内稳定。
- 安全、数据和租户影响已查清。
- 所有临时措施都有撤销、保留或长期化决定。
- 负责人确认可以解除发布冻结。

P0/P1 必须复盘；P2 在重复发生、影响扩大或暴露系统性问题时复盘。

## 常见降级方向

- 模型 Provider 异常：阻止新请求、切换已批准 Provider 或展示真实不可用状态。
- Voice Service/GPU 异常：关闭语音入口，停止队列，保留文本对话。
- Redis 异常：限制依赖短期协调状态的能力，避免错误地声称操作成功。
- PostgreSQL 异常：停止写操作或进入只读/维护状态，优先保护数据一致性。
- Embed 身份异常：暂停受影响应用或 exchange，不能降级为匿名绕过鉴权。
- 发布错误：暂停流量切换并回到已验证版本，保留版本和事件审计。

具体开关、命令和权限必须在生产架构确认后补充。

## 待确认

- 值班人员、事件指挥、安全和数据负责人的名单或岗位。
- 告警与事件沟通渠道、状态页和用户通知方式。
- 生产日志、指标、追踪、备份和凭据轮换工具。
- 各组件可用的降级开关、回滚命令和所需权限。
- 复盘完成时限及行动项跟踪系统。
