# 指标与可观察性

本文定义 Debussy 如何判断产品是否被成功使用、核心链路是否健康，以及发布后应观察什么。目标值未确认前使用“基线采集”，不得把建议值写成正式承诺。

## 指标原则

- 产品成功、用户体验和系统健康分别衡量，不能只用服务在线代表产品可用。
- Usage、延迟和错误率由服务端或可信遥测计算，前端只展示结果。
- 所有线上指标至少可按环境、Tenant、Agent、Published App 和 Revision/App Version 中适用的维度筛选。
- 日志、指标和追踪不得记录管理员凭据、终端用户令牌、完整用户文本或未脱敏附件内容。
- 指标定义发生变化时必须保留口径版本和生效时间。

## 产品漏斗

内部可用版本优先验证团队能否稳定完成文本 Agent 主链路，不设置外部客户增长或商业转化指标。

| 指标 | 定义 | 计算口径 | 当前状态 | 目标 |
| --- | --- | --- | --- | --- |
| Agent 创建成功率 | 开始创建后成功保存 Agent 的比例 | 成功保存 Agent 数 / 创建流程开始数 | 待补事件口径 | 待确认 |
| Revision 验证率 | 已保存 Revision 中至少完成一次成功 Chat 调试的比例 | 有成功调试的 Revision 数 / 已保存 Revision 数 | 可由会话与版本关联推导，待验证 | 待确认 |
| 发布转化率 | 已验证 Revision 中成功发布的比例 | 成功发布 Revision 数 / 已验证 Revision 数 | 发布数据已具备，漏斗口径待补 | 待确认 |
| 首次发布耗时 | 从首次创建 Agent 到首次成功激活应用的时间 | 按 Agent 统计中位数及 P90 | 待补统一时间口径 | 待确认 |
| 有效应用率 | 统计周期内至少完成一次终端用户对话的已激活应用比例 | 有有效对话应用数 / 已激活应用数 | Conversation 数据已具备，待补报表 | 待确认 |
| 回滚率 | 发布后需要回滚的版本比例 | 回滚版本数 / 激活版本数 | 发布事件已具备，待补聚合 | 先采基线 |

## 用户体验指标

| 指标 | 定义 | 建议统计 | 当前状态 | 目标 |
| --- | --- | --- | --- | --- |
| 对话成功率 | 用户轮次最终正常完成的比例 | 总体、按来源、模型、应用版本 | Runtime 事件和测试已覆盖，线上看板待补 | 待确认 |
| 首事件延迟 | 请求被接受到首个可展示事件的时长 | P50/P95/P99 | 服务端已有性能统计基础 | 待确认 |
| 完整轮次延迟 | 请求被接受到轮次终止的时长 | P50/P95/P99 | 服务端已有性能统计基础 | 待确认 |
| 实时连接成功率 | WebSocket/Realtime 建连成功比例 | 按入口、应用和失败码 | 连接与容量测试已存在 | 待确认 |
| 附件成功率 | 合法附件从上传到会话可用的比例 | 按类型、大小和失败码 | 上传、配额和扫描测试已存在 | 待确认 |
| 语音首包延迟 | 发起 TTS 到收到首个 PCM chunk 的时长 | 冷启动与热启动分别统计 P50/P95 | Voice Service 有手动 smoke 工具 | 待确认 |
| 语音中断率 | 非用户主动取消的播放异常终止比例 | 按 Provider、设备和失败码 | 待补线上遥测 | 待确认 |

## 系统健康指标

| 指标 | 维度 | 发布后用途 | 目标/告警 |
| --- | --- | --- | --- |
| HTTP 请求量、错误率和延迟 | Plane、路由、状态码 | 判断控制面和数据面回归 | 待确认 |
| WebSocket 活跃连接与异常断开 | 环境、应用、关闭码 | 判断实时链路容量与稳定性 | 待确认 |
| Runtime 轮次成功、失败、取消 | Agent、Revision、模型、来源 | 定位模型与执行器故障 | 待确认 |
| Provider 错误率和延迟 | Provider、模型、错误码 | 降级或切换模型依据 | 待确认 |
| PostgreSQL 连接、查询错误和延迟 | 环境、操作类型 | 判断持久层健康 | 待确认 |
| Redis 连接、命令错误和延迟 | 环境、用途 | 判断协调与短期状态健康 | 待确认 |
| Token 用量 | Tenant、Agent、来源、模型 | 成本核对和异常检测 | 已有 Usage 契约；预算待确认 |
| TTS 请求、失败、首包和 RTF | Provider、模型、冷/热启动 | 判断语音体验和 GPU 容量 | 待确认 |
| 备份成功与最近恢复点时间 | 备份类型、结果 | 判断 24 小时 RPO 是否满足 | 内部使用前启用；每日成功，最近恢复点不超过 24 小时 |
| 恢复耗时 | 从决定恢复到文本主链路验证通过 | 判断 4 小时 RTO 是否满足 | 内部使用前演练；不超过 4 小时，仅适用于当前机器和本地备份可用的事件 |

内部版本的容量基线为约 10～20 名团队成员、20 个同时进行的文本对话；30 个同时在途轮次自动化验证提供最低安全余量。该口径不延伸为公网容量承诺。

## 事件与归因要求

产品漏斗至少需要以下服务端事实或可信事件：

- Agent 创建和保存成功。
- Revision 创建、Chat 调试开始及成功结束。
- 应用创建、版本激活、暂停和回滚。
- Embed bootstrap、凭据交换和 Conversation 创建。
- 轮次开始、首事件、成功、失败和取消。

每条事件至少包含：事件名、口径版本、服务端时间、环境、Tenant、关联对象 ID、来源和结果码。用户主体只能使用允许分析的匿名或脱敏标识。

## 发布观察窗口

每次发布至少比较发布前基线与发布后窗口：

1. 发布前记录当前请求量、错误率、延迟、连接数和资源状态。
2. 发布后立即执行冒烟验证。
3. 在确认后的观察窗口内持续比较核心指标。
4. 任一发布阻断指标越界时按 [`RELEASE-SOP.md`](./RELEASE-SOP.md) 决定停止、降级或回滚。

观察窗口时长、采样频率和回滚阈值均待生产环境与流量规模确认。

## 看板最小集合

- 产品漏斗：创建 Agent → 保存 Revision → 成功调试 → 发布 → 首次有效对话。
- 实时体验：请求量、成功率、首事件延迟、完整轮次延迟和异常断开。
- 发布对比：按 App Version 对比错误率、延迟和回滚事件。
- 成本用量：按 Tenant、Agent、来源和模型统计 Token。
- 恢复状态：最近一次成功备份时间、备份连续性和最近一次恢复演练结果。

语音健康看板在 R3 开始前补齐，不阻断内部文本版本。

## 待确认

- 内部版本是否以“每周成功完成至少一次文本 Agent 主链路的团队成员数”作为北极星指标。
- 产品漏斗各阶段的正式事件名和数据保留周期。
- 对话、连接、附件和语音的 SLO 目标。
- Token 或金额预算及异常增长阈值。
- 使用何种监控、日志、追踪和告警平台。
- 指标与告警的负责人及通知渠道。
