# 发布与回滚 SOP

本文定义 Debussy 版本从候选到发布、观察和回滚的标准流程。当前仓库只证明本地开发与发布能力验证，生产基础设施和自动化部署尚未确认，因此生产命令不得从本文推断或临时编造。

当前流程只服务于团队日常使用的内部版本，重点是文本 Agent 主链路稳定、可观察、可回滚和数据可恢复；不包含公网或面向外部客户的发布。

当前发布目标是开发机上的单机内部环境。迁移至局域网服务器前，必须另行确认网络、身份、TLS、备份和部署方式，不得直接照搬仅监听 `127.0.0.1` 的开发配置。

## 适用范围

- Debussy 管理员工作台、Embed Chat、Control/Data/Runtime Plane。
- PostgreSQL、Redis、Voice Service、Avatar 包及其配置或契约变更。
- 紧急修复仍须执行标记为“不可跳过”的步骤。

不适用于上游 Pi npm 包的独立发布；该流程遵循 `runtimes/pi/AGENTS.md` 的 lockstep release 规则。

## 角色

同一人可以兼任多个角色，但每次发布必须在记录中明确：

- 发布负责人：协调步骤、维护时间线并作出停止决定。
- 变更负责人：解释变更、验证功能并处理回归。
- 验收负责人：确认产品主链路和已知风险。
- 运维负责人：执行部署、观察指标和回滚。
- 安全/数据负责人：在涉及权限、凭据、迁移或敏感数据时审核。

当前由产品负责人承担最终产品验收与发布放行。涉及技术、安全、数据和恢复门禁时，产品负责人不得以单方放行替代对应证据；协助人与替代放行人待团队角色明确后补充。

## 发布输入

进入发布流程前必须具备：

- 唯一的候选版本或 Git 提交。
- 本次变更范围、非范围和受影响组件。
- 数据库、配置、密钥、依赖及外部 Provider 变化清单。
- 对应开发规格、验收标准和发布说明。
- 自动化及人工验收证据。
- 回滚目标、回滚步骤和数据兼容性说明。
- 已知问题、风险接受和负责人。

## 标准流程

### 1. 建立发布候选

1. 冻结候选提交，不在验证期间静默替换代码。
2. 核对锁文件、子模块、环境变量和数据库迁移。
3. 对照路线图确认变更属于本次发布范围。
4. 为每项高风险变更指定验证和回滚方式。

### 2. 执行质量门禁（不可跳过）

按 [`QUALITY.md`](./QUALITY.md) 执行适用门禁。Pi Runtime 的当前基础命令为：

```bash
cd runtimes/pi
npm run check
./test.sh
```

涉及发布与 Embed 时追加：

```bash
bash scripts/verify-publishing-mvp.sh
bash scripts/verify-publishing-browser.sh
```

涉及真实模型、Voice Service、GPU、外部存储或生产凭据的测试必须在受控环境单独执行，不得混入无凭据自动化测试。

### 3. 发布前检查（不可跳过）

- 确认目标环境、Tenant 范围和部署对象。
- 确认当前线上版本和计划发布版本。
- 确认数据库备份、迁移前置条件和恢复方式。
- 确认配置和密钥通过安全渠道提供，不进入仓库、命令记录或日志。
- 记录发布前 [`METRICS.md`](./METRICS.md) 基线。
- 确认监控、日志、告警和负责人在线。
- 向受影响人员发送发布窗口、影响和回滚条件。

### 当前单机数据边界

- PostgreSQL 数据保存在 Docker 命名卷 `pi-admin-dev-postgres`，是当前需要备份和验证恢复的主要持久数据。
- Redis 配置为不生成 RDB、不启用 AOF，只承担可丢失的短期状态；重启后应通过重新建连恢复，不纳入数据备份。
- 管理员令牌、Embed 签名密钥、subject pepper 和 bootstrap Tenant ID 默认保存在 `runtimes/pi/.pi/admin-dev/`；它们属于敏感恢复材料，备份时必须加密并限制访问。
- `.env.web.local` 是机器配置，不提交 Git；迁移或恢复时应从安全配置源重建。
- 当前仓库尚无正式备份脚本；需按已确认的 24 小时 RPO 固化 `pg_dump`/恢复和敏感状态目录备份步骤。

### 单机备份要求

本节是进入内部日常使用前的落实要求，目前尚未执行或启用：

- 恢复点目标（RPO）为 24 小时：数据库和身份材料每天至少成功备份一次。
- 恢复时间目标（RTO）为 4 小时：当前机器和本地备份可用时，应在决定恢复后 4 小时内恢复文本 Agent 主链路。
- 备份保留 14 天，按日期生成不可覆盖的备份集。
- 每个备份集至少包含 PostgreSQL 逻辑备份、`runtimes/pi/.pi/admin-dev/` 敏感恢复材料和恢复所需的配置清单；代码使用 Git 提交恢复，不复制工作区作为代码备份。
- 备份保存在当前机器，但必须位于仓库、Docker 命名卷和当前应用数据目录之外；仅留在同一 Docker 卷不算备份。
- 敏感恢复材料必须加密保存，备份文件和解密凭据不得位于同一位置。
- 每次备份记录开始/完成时间、源版本、文件校验值、结果和失败原因。
- 删除超过 14 天的备份前，必须确认最近一次备份成功且至少存在一份已验证可恢复的备份。
- 至少每月执行一次恢复演练；首次内部可用发布前必须成功演练一次。

计划使用本机目录 `/home/hello/backups/debussy`，每日 03:00 自动执行，保留 14 天；失败写入本地日志，当前不接外部告警平台。仓库应在接近内部可用阶段时提供备份、校验和恢复脚本，并经确认后再启用定时任务。未经恢复演练的备份不能视为已满足恢复要求。

已接受风险：当前阶段不复制到 NAS、其他电脑、移动介质或云存储。当前机器、系统盘或同时承载备份的存储介质损坏时，24 小时 RPO 和 4 小时 RTO 均无法保证；此风险必须在迁移到局域网服务器前重新评估。

### 4. 执行部署

生产部署平台和命令待确认。执行时必须：

1. 只部署已验证的候选版本。
2. 先执行可向后兼容的数据变更，再切换应用流量。
3. 每一步记录开始、结束、执行人、结果和输出证据位置。
4. 任一步结果不明确时停止，不继续叠加变更。
5. 不在发布窗口临时修改生产数据库、密钥或未评审代码。

### 5. 发布后冒烟（不可跳过）

- 管理员能够进入正确 Tenant，读取真实状态。
- Agent 和 Revision 可读取，管理员 Chat 可完成一轮真实对话。
- 发布应用指向预期 Revision/App Version。
- Embed bootstrap、凭据交换、建连和一轮对话成功。
- 发布对话页在最新版稳定版电脑 Chrome、真实 Android Chrome 和真实 iOS Safari 中完成进入、阅读、输入、发送及失败恢复；虚拟键盘不遮挡核心操作。
- Usage 记录来源和 Token，Session 日志可追溯应用与版本。
- 暂停/回滚入口可用，且当前回滚目标仍可部署。
- R3 涉及语音时，追加验证 TTS、取消、文本降级和 Avatar 状态恢复；不阻断当前内部文本版本。
- 容量验证覆盖 20 个同时进行的文本对话，并确认 30 个同时在途轮次自动化门禁通过。

### 6. 观察与确认

- 在确认后的观察窗口内监控错误率、延迟、连接、Provider、数据库、Redis 和 Token 用量。
- 对比发布前基线，并按应用版本分组检查。
- 无阻断项且指标稳定后，由发布负责人宣布完成。
- 保存发布记录、验收证据、指标截图/链接和已知问题。

## 回滚

### 触发条件

出现以下任一情况应立即停止发布并优先回滚或降级：

- P0 缺陷、安全或 Tenant 隔离问题。
- 数据损坏、迁移异常或凭据暴露风险。
- 主链路不可用、错误率或延迟超过确认阈值。
- 无法观察真实状态，无法判断影响范围。
- 外部 Provider 故障且既定降级不能恢复服务。

### 回滚步骤

1. 宣布进入回滚，冻结新的非必要变更。
2. 记录故障开始时间、影响范围和当前版本。
3. 停止流量切换；可降级时先关闭受影响能力并保留文本主链路。
4. 将应用或发布对象切回已验证版本。
5. 仅在明确兼容且有恢复方案时回滚数据库；优先使用向前修复或兼容迁移。
6. 重跑发布后冒烟并确认关键指标恢复。
7. 通知相关人员结果，转入 [`INCIDENT-SOP.md`](./INCIDENT-SOP.md) 跟踪。

## 紧急发布

紧急发布可以缩短评审和观察准备，但不得跳过：

- 候选版本唯一性。
- 受影响范围与回滚方案。
- 相关自动化测试和最小人工冒烟。
- 安全、租户隔离和数据兼容检查。
- 发布后观察与事件记录。

- 单机本地备份的加密工具，以及何时开始实现和启用自动调度。
- 局域网服务器的操作系统、访问入口、TLS、数据库/Redis 拓扑和部署工具。
- 标准发布窗口、观察时长及通知渠道。

- 正式回滚阈值和紧急发布批准规则。
