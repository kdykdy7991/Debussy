# 问答笔记

## 1. Pi Agent 如何统计 TPS 和 Token 指标？

### 问题

> TPS 121.5 tok/s. out 186, in 4,744, cache r/w 0/0, total 4,930, 1.5s
>
> 以我当前的模型为例，Pi Agent 是如何统计出这些指标的？

### 回答

这行指标由项目扩展 `.pi/extensions/tps.ts` 生成，不是 Pi 核心内置统计。

扩展在收到 `agent_start` 事件时通过 `Date.now()` 记录开始时间，在收到 `agent_end` 时计算整个 Agent 回合的耗时。然后遍历该回合产生的所有 assistant message，将其中的 usage 累加：

```ts
input += message.usage.input || 0;
output += message.usage.output || 0;
cacheRead += message.usage.cacheRead || 0;
cacheWrite += message.usage.cacheWrite || 0;
totalTokens += message.usage.totalTokens || 0;
```

这些 token 数通常来自 OneAPI 响应中的 usage，由对应 API adapter 转换为 Pi 的统一字段，并不是 Pi 在本地重新分词计算的。如果一次 Agent 回合包含工具调用和多次模型请求，扩展会把该回合内所有 assistant message 的 usage 累加。

TPS 的公式是：

```text
TPS = output tokens ÷ Agent 回合总耗时秒数
```

当前数据中：

```text
186 ÷ 121.5 ≈ 1.531 秒
```

界面显示 `1.5s`，是因为耗时使用 `toFixed(1)` 保留一位小数。

各字段含义：

- `out 186`：模型报告的输出 token 数。
- `in 4,744`：输入 token 数，可能包括 system prompt、上下文文件、skills、历史消息、工具定义和当前问题。
- `cache r/w 0/0`：prompt cache 读取和写入 token 数。为零表示未使用缓存，或 OneAPI 没有报告缓存 usage。
- `total 4,930`：总 token 数；本次正好是 `4,744 + 186`。
- `1.5s`：从 `agent_start` 到 `agent_end` 的墙钟时间。

这里的 TPS 是整个 Agent 回合的平均输出吞吐率，不是严格的模型解码速度。计时可能包含网络延迟、首 token 等待、工具执行和多次模型请求。若要测纯生成速度，应统计首个输出 token 到最后一个输出 token 之间的时间。

相关代码：

- `.pi/extensions/tps.ts`
- `packages/ai/src/types.ts`

## 2. Pi 如何管理会话，旧会话保存后有什么用？

### 问题

> 目前项目的会话是如何管理的？每次都是新的会话吗？老的会话记录还保存吗？如果保存了，保存有什么用？

### 回答

不带会话参数直接启动 Pi 时，默认调用 `SessionManager.create()` 创建一个新会话。旧会话不会被覆盖，正常情况下会按当前工作目录分类保存为 JSONL：

```text
~/.pi/agent/sessions/--<工作目录>--/<时间戳>_<UUID>.jsonl
```

会话文件采用延迟落盘：创建会话时先在内存中建立 header；只有产生 assistant 回复后才把完整内容写入文件，以避免仅启动后退出也产生空会话。使用 `--no-session` 时则只在内存中运行，不会保存。

每条记录具有 `id` 和 `parentId`，因此一个会话文件不是简单的线性聊天文本，而是 append-only 的会话树。文件可以记录：

- 用户、assistant 和工具消息。
- 模型及 thinking level 变化。
- compaction 和 branch summary。
- 分支、标签和 extension 自定义状态。
- token usage、成本和错误信息等消息元数据。

旧会话的主要用途：

1. `pi -c` 或 `--continue` 继续当前项目最近的会话。
2. `pi -r`、`--resume` 或 `/resume` 查找并恢复历史会话。
3. `--session <path|id>` 精确打开某个会话。
4. `/tree` 回到历史节点并从那里创建新分支，旧分支不会被删除。
5. `/fork` 和 `/clone` 从历史上下文生成独立的新会话文件。
6. `/export` 导出对话，或用于检查模型调用、工具执行和 token 消耗。
7. 长对话压缩后仍保留原始历史；发送给模型的是 `buildSessionContext()` 根据当前活动分支和 compaction 构造出的上下文，不是无条件重放整个文件。

常用命令：

```bash
pi -c                  # 继续当前项目最近的会话
pi -r                  # 选择历史会话
pi --session <path|id> # 打开指定会话
pi --no-session        # 临时会话，不落盘
```

交互模式中可使用 `/session` 查看当前会话 ID、文件位置、消息数、token 和成本。

相关代码与文档：

- `packages/coding-agent/src/main.ts` 中的 `createSessionManager()`
- `packages/coding-agent/src/core/session-manager.ts`
- `packages/coding-agent/docs/sessions.md`
- `packages/coding-agent/docs/session-format.md`

## 3. TUI 是否与 Agent 核心完全解耦，可以换成 Web 或微信？

### 问题

> 我目前理解，TUI 和实际对话是完全解耦的。也就是说，我完全可以通过 Web 网页、小程序甚至微信，和当前 Agent 中的核心 loop 交互。

### 回答

这个理解基本正确，但不能称为完全解耦。

模型请求和工具循环位于 `packages/agent`，`AgentSession` 在其上增加会话持久化、上下文压缩、资源加载和扩展机制。这些核心能力不依赖终端，可以被 TUI、RPC、Web 服务或其他消息入口复用。

当前架构中的层次大致是：

```text
Web / 小程序 / 微信 / TUI
            ↓
       接入与协议层
            ↓
 AgentSessionRuntime / AgentSession
            ↓
    packages/agent 核心 loop
            ↓
       模型与工具调用
```

但是 `InteractiveMode` 除了显示界面，还实现了一些交互业务：

- slash commands。
- 模型、会话和设置选择器。
- 项目信任及确认对话框。
- extension UI API。
- steering、follow-up 和队列展示。
- 终端快捷键和编辑器行为。

因此替换 TUI 时，普通对话、流式回复和工具事件可以直接复用核心；依赖终端控件的功能需要由新客户端重新实现，或者定义为平台无关的协议。

项目已经提供两条适合的接入路径：

1. RPC 模式：启动长期运行的 Pi 进程，通过 JSON 消息发送 prompt、接收流式事件、切换会话和取消请求。适合后端服务作为 Pi 的进程管理器。
2. SDK：在自己的 Node.js 服务中直接创建 `AgentSessionRuntime` 和 `AgentSession`。控制力更强，但需要自行处理实例生命周期、并发、认证和事件转发。

对于 Web、小程序和微信，推荐增加一个服务端适配层：外部平台只连接自己的 HTTP/WebSocket/Webhook 服务，服务端再调用 Pi RPC 或 SDK。不要让浏览器或微信客户端直接持有模型 API Key，也不要让多个用户共享同一个可写 session 实例。

需要按用户或会话隔离：

- `AgentSessionRuntime` 实例。
- session ID 和 JSONL 文件。
- 工作目录及工具权限。
- API 凭证和可用模型。
- 消息队列、取消信号和流式事件订阅。

相关代码与文档：

- `packages/agent/src/agent-loop.ts`
- `packages/coding-agent/src/core/agent-session.ts`
- `packages/coding-agent/src/core/agent-session-runtime.ts`
- `packages/coding-agent/src/modes/rpc/rpc-mode.ts`
- `packages/coding-agent/docs/rpc.md`
- `packages/coding-agent/docs/sdk.md`

## 4. 文本文件上传后是如何进入 LLM 的？

### 问题

> 目前是如何处理文件上传的，比如我上传了一个文本，具体走了那些步骤最后输入给了 LLM？

### 回答

当前 P1 的文本上传链路是“HTTP 上传文件，WebSocket 传附件引用，Agent 在执行回合前读取文件内容并临时注入 LLM”。文件二进制不会经过会话 WebSocket，也不会直接写入 transcript。

完整流程：

```text
浏览器选择文件
  ↓
HTTP multipart POST /api/pi/v2/uploads
  ↓
服务端校验、嗅探 MIME、写入受控暂存目录
  ↓
返回 attachment 元数据
  ↓
WebSocket attach_upload 绑定到当前 session
  ↓
发送 prompt + attachmentIds
  ↓
服务端校验附件属于当前 session，并解析为服务器内部文件路径
  ↓
AgentSession 读取文本，构造 user content blocks
  ↓
传给当前 LLM adapter
```

#### 1. 浏览器上传

`packages/web/src/lib/uploader.ts` 使用 `XMLHttpRequest` 发送 `multipart/form-data`：

```text
POST /api/pi/v2/uploads
Authorization: Bearer <PI_WEB_TOKEN>
FormData: files=<用户选择的文件>
```

使用 XHR 是为了获得上传进度。前端不会把文件内容编码后放进 WebSocket 消息。

#### 2. Server 接收和处理

`packages/server/src/web/uploads.ts` 使用 `busboy` 解析 multipart 请求，并执行：

- Host、Origin 和 Bearer token 校验。
- 单文件大小和单次文件数量限制。
- MIME 嗅探，并与文件扩展名交叉校验。
- 先写入临时文件，校验成功后移动到受控上传目录。
- 调用上传 pipeline 完成扫描、解析和索引阶段。
- 生成 `attachmentId`、文件名、媒体类型、大小、SHA-256 和状态等元数据。

上传成功后，浏览器只得到附件元数据，不会得到服务器真实路径。

#### 3. 绑定到会话

上传完成后，`SessionController.uploadFiles()` 自动通过 WebSocket 发送 `attach_upload`，把 ready 状态的附件绑定到当前 session。服务端会确认附件存在、状态为 `ready`，且没有绑定到其他 session。

绑定成功后，服务端广播 `attachment_snapshot`，Web 端在 composer 上方显示附件 chip。

#### 4. 发送问题时只传引用

用户发送问题时，WebSocket 的 `prompt` 命令携带：

```json
{
  "command": "prompt",
  "sessionId": "session-id",
  "text": "总结这个文件",
  "attachmentIds": ["upload-id"]
}
```

服务端不会信任客户端直接提供的路径，而是通过 `attachmentId` 查找记录，确认该附件属于当前 session 后，在服务端内部解析出受控文件路径。

#### 5. AgentSession 读取文本并构造消息

调用链是：

```text
ServerSession.prompt()
  → AgentSessionRuntime.prompt()
  → AgentSession.prompt(text, { attachments })
  → _buildAttachmentContent()
```

对于文本附件，`AgentSession._buildAttachmentContent()` 当前会：

- 从服务器暂存路径读取文件。
- 按 UTF-8 解码。
- 单个文本文件最多读取 256 KiB，超过部分截断。
- 超过限制时追加 `…(文件过长，已截断)`。
- 在内容前加入文件名标记。

例如用户输入“总结这个文件”，发送给 Agent 的 user message 内容会近似变成：

```text
总结这个文件

[附件: notes.txt]
这里是 notes.txt 的实际文本内容……
```

文本附件最终表现为 user message 中的额外 text content block，而不是新的独立 user 回合。

#### 6. 传给 LLM 和保存 transcript 是两条不同路径

实时发送给 LLM 的 user message 包含完整的文本附件内容，因此模型可以直接阅读文件内容。

但在 `message_end` 持久化用户消息时，`AgentSession` 会把 transcript 中的内容替换为引用：

```text
总结这个文件
[附件: notes.txt]
```

因此：

- LLM 输入：包含文本文件内容。
- JSONL transcript：只保存用户问题和附件文件名引用。
- transcript 不保存文件正文。
- transcript 不保存服务器暂存路径。
- 前端历史记录不会泄露文件内容。

图片走同一条上传和绑定流程，但在 `AgentSession` 中会读取文件、经过图片处理后生成 image content block；文本文件则生成 text content block。

当前 P1 是“全量注入”方案，不是 RAG/Citation 方案。文件内容是在每次带附件的 Agent 回合执行前读取并注入，P2 Citation/RAG 才会进一步讨论切片、检索、引用位置和来源展示。

- `packages/server/src/sessions.ts`

## 5. 文件内容如何继续走到 OpenAI SDK 的 `chat.completions.create`？

### 问题补充

> 上面的说明还不够详细，需要继续说明附件内容如何从 `AgentSession` 走到最终类似 OpenAI SDK 的 chat 接口，以及 `chat` 调用时具体传入什么。

### 回答

`AgentSession` 不直接调用 OpenAI SDK。它先把消息交给通用 Agent loop，Agent loop 再根据当前模型选择对应的 provider adapter。不同 provider 的最终 SDK 调用不同，但附件内容会在 adapter 层转换成该 provider 的标准消息格式。

完整调用链是：

```text
AgentSession.prompt()
  ↓
AgentSession._runAgentPrompt()
  ↓
packages/agent/src/agent-loop.ts
  ↓
streamAssistantResponse()
  ↓
config.transformContext(messages)
  ↓
config.convertToLlm(messages)
  ↓
llmContext = { systemPrompt, messages, tools }
  ↓
streamFunction(model, llmContext, options)
  ↓
packages/ai/src/api/<provider-api>.ts
  ↓
convertMessages() / buildParams()
  ↓
OpenAI SDK 或 Anthropic SDK
```

#### 1. AgentSession 先构造内部消息

用户问题和附件内容首先构造成 Pi 内部的 `Message`：

```ts
{
  role: "user",
  content: [
    { type: "text", text: "总结这个文件" },
    { type: "text", text: "[附件: notes.txt]\\n文件正文……" }
  ],
  timestamp: 1786065530000
}
```

这时附件正文已经进入内存中的 user message，但还没有变成 OpenAI 或 Anthropic 的参数对象。

同时，AgentSession 会设置 `_pendingAttachmentReferenceText`，用于后续持久化时把同一条用户消息改成引用版本。这个替换只影响 transcript，不影响当前正在发送给模型的内存消息。

#### 2. Agent loop 合并上下文

`packages/agent/src/agent-loop.ts` 的 `streamAssistantResponse()` 会把当前会话上下文合并起来，包括：

- system prompt。
- 历史 user/assistant/tool messages。
- 当前包含附件正文的 user message。
- 工具定义 `tools`。
- 当前模型和 thinking 配置。

然后执行两个转换钩子：

```ts
messages = await config.transformContext(messages, signal);
const llmMessages = await config.convertToLlm(messages);
```

这里的 `convertToLlm` 负责把 Agent 层允许的 `AgentMessage` 转换成模型层的 `Message`。附件文本仍然是普通的 text content，不会在这里重新读取文件。

之后形成统一的 LLM 上下文：

```ts
const llmContext = {
  systemPrompt,
  messages: llmMessages,
  tools,
};
```

#### 3. OpenAI Chat Completions 兼容模型

如果当前模型的 API 类型是 `openai-completions`，会进入：

```text
packages/ai/src/api/openai-completions.ts
```

该 adapter 的 `convertMessages()` 会把 Pi 的 text content 转为 OpenAI Chat Completions 的 `ChatCompletionContentPartText`。

简化后的最终参数近似是：

```ts
const params = {
  model: model.id,
  stream: true,
  messages: [
    {
      role: "system",
      content: "系统提示词……",
    },
    // 这里可能还有历史消息、工具调用和工具结果
    {
      role: "user",
      content: [
        {
          type: "text",
          text: "总结这个文件",
        },
        {
          type: "text",
          text: "[附件: notes.txt]\\n文件正文……",
        },
      ],
    },
  ],
  tools: [/* Agent 工具定义 */],
  stream_options: { include_usage: true },
};
```

随后调用 OpenAI SDK：

```ts
const { data: openaiStream, response } = await client.chat.completions
  .create(params, requestOptions)
  .withResponse();
```

因此，对于 OpenAI Chat Completions 兼容接口，文本文件不是作为文件 URL 或独立参数传入，而是已经拼进：

```text
messages[n].content[k].text
```

也就是同一条 user message 里的一个文本内容块。

如果是图片，adapter 会把图片 content 转成：

```ts
{
  type: "image_url",
  image_url: {
    url: "data:image/png;base64,<base64>"
  }
}
```

文本文件目前不会转成 data URL，而是直接转成文本块。

#### 4. Anthropic Messages API

如果当前模型的 API 类型是 `anthropic-messages`，会进入：

```text
packages/ai/src/api/anthropic-messages.ts
```

此时 user message 近似变成：

```ts
{
  role: "user",
  content: [
    {
      type: "text",
      text: "总结这个文件",
    },
    {
      type: "text",
      text: "[附件: notes.txt]\\n文件正文……",
    },
  ],
}
```

然后构造：

```ts
const params = {
  model: model.id,
  max_tokens: ...,
  system: "系统提示词……",
  messages,
  tools,
  stream: true,
};
```

最后调用 Anthropic SDK 的：

```ts
client.messages.create({ ...params, stream: true }, requestOptions)
```

因此无论是 OpenAI Chat Completions 还是 Anthropic Messages，附件文本的共同点都是：

```text
附件正文 → 当前 user message 的 text content block → provider adapter → SDK messages 参数
```

#### 5. 模型返回和前端流式显示

OpenAI SDK 或 Anthropic SDK 返回流式事件后，provider adapter 会把各厂商事件统一转换为 Pi 的 `AssistantMessageEvent`，例如：

```text
text_start
text_delta
thinking_delta
toolcall_delta
text_end
done
```

Agent loop 再把这些事件转成 `AgentEvent`，`AgentSession` 转发给 Server，Server 通过 Pi WebSocket 协议发送给 Web 客户端。前端看到的流式回答，就是这条反向链路产生的：

```text
LLM SDK stream
  → provider adapter
  → AssistantMessageEvent
  → Agent loop
  → AgentSession
  → Server event log
  → WebSocket event
  → Web UI
```

#### 6. 一个重要结论

当前 P1 并没有把文本文件上传给 OpenAI 的 Files API，也没有在模型侧传 `file_id`。实际做法是：

```text
本地文件 → Server 读取文本 → 拼进 messages 的 text content → 调用 chat/messages API
```

所以它属于“应用层全量注入”。文本过长时会在 AgentSession 的读取阶段截断，而不是让模型 API 自己处理文件检索。P2 Citation/RAG 如果实现，将在这条链路之前增加切片、检索和引用来源生成。

相关代码：

- `packages/coding-agent/src/core/agent-session.ts`
- `packages/agent/src/agent-loop.ts`
- `packages/ai/src/api/openai-completions.ts`
- `packages/ai/src/api/anthropic-messages.ts`
- `packages/ai/src/api/transform-messages.ts`

## 6. 图片附件与文本附件在流程上有什么区别？

### 问题

> 如果上传的是图片，和文本文件相比，流程上有什么区别？

### 回答

上传、鉴权、暂存、绑定会话和发送 `attachmentIds` 的前半段完全相同。主要区别从 `AgentSession._buildAttachmentContent()` 开始：

```text
文本：读取文件 → UTF-8 解码 → text content block
图片：读取文件 → processImage() → base64 image content block
```

#### 1. Server 上传阶段基本相同

图片仍然通过：

```text
POST /api/pi/v2/uploads
  → busboy
  → MIME 嗅探和扩展名校验
  → 受控暂存目录
  → Attachment 元数据
  → attach_upload
```

服务端保存的是图片文件和元数据，WebSocket 仍然只传 `attachmentId`，不会传图片二进制。

#### 2. AgentSession 读取图片

发送 prompt 时，Server 根据 `attachmentId` 解析出内部文件路径，传给 `AgentSession`。

对于 `image/*` 附件，`AgentSession._buildAttachmentContent()` 会：

1. 从受控路径读取原始图片字节。
2. 调用 `processImage(content, mediaType, { autoResizeImages: true })`。
3. 根据处理结果生成内部图片块：

```ts
{
  type: "image",
  mimeType: "image/png",
  data: "<base64 image data>"
}
```

4. 另外追加一个文本标记：

```ts
{
  type: "text",
  text: "[附件: red-circle.png]"
}
```

所以内部 user message 近似是：

```ts
{
  role: "user",
  content: [
    { type: "text", text: "描述这张图片" },
    { type: "image", mimeType: "image/png", data: "..." },
    { type: "text", text: "[附件: red-circle.png]" }
  ]
}
```

图片正文不会转成 OCR 文本；它以图像 content block 交给视觉模型。

#### 3. OpenAI Chat Completions 的最终形态

`packages/ai/src/api/openai-completions.ts` 的 `convertMessages()` 会将内部 image block 转成 OpenAI 的 `image_url`：

```ts
{
  role: "user",
  content: [
    {
      type: "text",
      text: "描述这张图片"
    },
    {
      type: "image_url",
      image_url: {
        url: "data:image/png;base64,<base64 image data>"
      }
    },
    {
      type: "text",
      text: "[附件: red-circle.png]"
    }
  ]
}
```

最终仍然进入：

```ts
client.chat.completions.create({
  model,
  messages,
  stream: true,
  tools,
});
```

区别是文本附件的正文位于 `type: "text"`，图片附件位于 `type: "image_url"`，使用 data URL 携带 base64 数据。

#### 4. Anthropic Messages 的最终形态

`packages/ai/src/api/anthropic-messages.ts` 会把内部 image block 转成 Anthropic 的 base64 source：

```ts
{
  role: "user",
  content: [
    {
      type: "text",
      text: "描述这张图片"
    },
    {
      type: "image",
      source: {
        type: "base64",
        media_type: "image/png",
        data: "<base64 image data>"
      }
    },
    {
      type: "text",
      text: "[附件: red-circle.png]"
    }
  ]
}
```

然后进入：

```ts
client.messages.create({
  model,
  system,
  messages,
  tools,
  stream: true,
});
```

#### 5. 如果当前模型不支持图片

模型元数据中的 `model.input` 用来标记是否支持 image input。

在 `packages/ai/src/api/transform-messages.ts` 中，如果模型不包含 image 能力，图片 block 会被替换为：

```text
(image omitted: model does not support images)
```

这意味着：

- 上传接口可能成功。
- 附件也可能成功绑定到 session。
- 但最终发送给不支持视觉的模型时，不会发送图片二进制。
- 模型只能看到图片被省略的占位文本和文件名标记。

因此，图片联调必须选择支持 image input 的模型，不能只依据“上传成功”判断模型能看图。

#### 6. Transcript 仍然只保存引用

图片和文本一样，实时 LLM 请求包含实际内容，但持久化 transcript 只保存：

```text
描述这张图片
[附件: red-circle.png]
```

不会保存 base64、图片正文或服务器路径。

#### 7. 核心差异总结

| 环节 | 文本附件 | 图片附件 |
| --- | --- | --- |
| 上传通道 | HTTP multipart | HTTP multipart |
| WebSocket | 只传 attachmentId | 只传 attachmentId |
| Agent 读取 | UTF-8 文本 | 原始字节 + 图片处理 |
| 内部 content | `type: "text"` | `type: "image"` |
| OpenAI Chat | `type: "text"` | `type: "image_url"` + data URL |
| Anthropic | `type: "text"` | `type: "image"` + base64 source |
| 不支持模型 | 正常发送文本 | 替换为图片省略占位符 |
| transcript | 文件名引用 | 文件名引用 |

当前 P1 图片处理也是“直接注入当前模型请求”，还没有 OCR、图片向量化、图像检索或 Citation。那些属于后续能力，不是当前上传流程的一部分。

相关代码：

- `packages/coding-agent/src/core/agent-session.ts`
- `packages/ai/src/api/transform-messages.ts`
- `packages/ai/src/api/openai-completions.ts`
- `packages/ai/src/api/anthropic-messages.ts`

## 7. 是否只需要分类文件并提供图片 Base64？

### 问题

> 也就是说传什么类型，这些 OpenAI 的 SDK 已经都适配了，我只需要做好分类，提供好图片的 Base64 格式数据？

### 回答

基本理解正确，但要区分“内部统一格式”和“OpenAI SDK 专用格式”。业务层不应该直接生成 OpenAI 的 `image_url` 对象，而应该提供项目内部统一的 `ImageContent`：

```ts
{
  type: "image",
  mimeType: "image/png",
  data: "<base64 data>"
}
```

然后由 provider adapter 负责转换：

```text
内部 ImageContent
  ├── OpenAI Chat Completions → image_url + data URL
  ├── Anthropic Messages      → image + base64 source
  ├── Google                  → inlineData
  └── 不支持图片的模型         → 图片占位文本
```

因此，上传和 Agent 层主要负责：

1. 判断附件类别：文本、图片或其他类型。
2. 由服务端 MIME 嗅探确定真实媒体类型，不只相信文件扩展名。
3. 文本读取为 UTF-8 text block。
4. 图片读取字节并通过统一图片处理器生成规范化 Base64 数据。
5. 产出内部 `TextContent` / `ImageContent`。
6. 根据模型能力决定是否发送图片，或者替换成占位文本。

OpenAI SDK 的适配代码已经存在于 `packages/ai/src/api/openai-completions.ts`，所以业务代码不需要自己拼：

```ts
{
  type: "image_url",
  image_url: {
    url: "data:image/png;base64,..."
  }
}
```

当前图片处理器还负责必要的格式和尺寸规范化，例如自动缩放；不能简单地把任意文件字节直接标记成图片。最终需要保证：

```text
mimeType 与实际内容一致
Base64 可被目标 SDK 接受
模型 input 声明支持 image
```

文本则不需要 Base64，直接提供：

```ts
{
  type: "text",
  text: "文件正文"
}
```

另外，“OpenAI SDK 已经适配了”只适用于对应 API 类型和支持的内容格式。OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 等接口的字段不同，统一适配应继续放在 `packages/ai`，不要让上传服务或 Web 页面感知 provider 差异。

核心原则：

```text
文件分类和内容提取由上传/Agent 层负责
provider-specific payload 由 packages/ai 负责
```

## 8. 谁定义了图片必须使用 Base64？这是模型厂商一开始就规定的吗？

### 问题

> 图片的 Base64 要求是谁定义的？是模型厂商一开始就规定的吗？

### 回答

需要区分两件事：

1. 模型厂商最终 API 接受什么格式。
2. Pi 内部统一消息类型选择什么格式。

当前项目中的 Base64 要求主要来自 Pi 自己的内部类型设计，而不是 OpenAI SDK 规定所有应用必须先把图片转成 Base64。

类型定义在：

```text
packages/ai/src/types.ts
```

```ts
export interface ImageContent {
  type: "image";
  data: string; // base64 encoded image data
  mimeType: string;
}
```

这说明 `ImageContent` 作为 Pi 内部 provider-neutral 中间格式时，约定 `data` 字段保存 Base64。它是项目内部的统一抽象，方便 Agent 层不关心当前使用 OpenAI、Anthropic、Google 还是其他 provider。

模型厂商定义的是各自 API 的最终 wire format，并不完全相同：

```text
OpenAI Chat Completions
  → image_url.url，可以是 data URL，也可以是远程 URL

OpenAI Responses
  → 根据输入类型支持不同的图片引用形式

Anthropic Messages
  → image source，可以使用 base64 等形式

Google Gemini
  → inlineData，通常包含 mimeType 和 base64 数据
```

Pi 选择 Base64 作为内部统一格式，主要是工程上的共同分母：

- 文件已经在 Server 本地，读取字节后即可编码。
- 不需要额外部署公开图片 URL。
- 不需要处理图片 URL 的鉴权、过期和访问权限。
- 可以在请求前统一缩放、转换格式和控制大小。
- 同一份 `ImageContent` 可以由各个 provider adapter 转换。
- 不让上传层和 Agent 层绑定 OpenAI 专用的 `image_url` 结构。

因此不是“OpenAI 规定了 Pi 必须使用 Base64”，而是：

```text
模型厂商规定各自最终请求格式
Pi 选择 Base64 作为内部统一图片表示
provider adapter 再把内部格式转换成厂商格式
```

当前调用关系是：

```text
原始图片二进制
  → processImage()
  → ImageContent.data = Base64
  → OpenAI adapter: data URL / image_url
  → Anthropic adapter: source.base64
  → Google adapter: inlineData
```

未来如果某个 provider 更适合使用图片 URL、文件 ID 或 Files API，应该只修改对应的 `packages/ai` adapter，原则上不需要改变：

- Web 上传接口。
- AttachmentStore。
- `AgentSession` 的附件解析流程。
- 内部 `ImageContent` 类型。

如果未来希望减少 Base64 的内存和请求体开销，也可以新增独立的图片引用类型，例如 `ImageUrlContent` 或 `FileReferenceContent`，但这属于协议和中间层的扩展，不应直接把某个 provider 的专用字段塞进现有 `ImageContent`。
