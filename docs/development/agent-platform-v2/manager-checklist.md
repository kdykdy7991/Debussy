# Agent 平台 V2 管理节奏检查清单

本文供产品负责人管理前端、后端和总架构师的工作节奏。技术细节以[实施总计划](./README.md)、[前端任务单](./frontend.md)、[后端任务单](./backend.md)和[验收任务单](./architect-acceptance.md)为准。

## 使用规则

- 只有看到可复核证据后才勾选，不接受“已经差不多”“本地能跑”等口头完成。
- 每项证据至少包含负责人、提交版本、测试/验收结果和遗留风险。
- 当前里程碑的“允许进入下一阶段”未勾选前，不启动下一个里程碑的正式实现。
- 前端可以在 DTO 冻结前做页面骨架和交互状态，但不能自行确定服务端字段和统计口径。
- 总架构师不替前后端实现；发现问题后退回相应负责人修复，再验收新候选。
- 新发现的范围不能直接插入开发，先判断是本里程碑阻断项还是放入后续里程碑。

## G. 每个里程碑固定管理节奏

每进入一个新里程碑，复制并执行本节：

- [ ] 启动会：三人确认范围、非范围、契约、负责人和验收场景。
- [ ] 方案门禁：通用能力先完成现有方案调研、最小原型和复用/自研决定。
- [ ] 后端先交付冻结契约、fixture 和错误语义。
- [ ] 架构师在正式实现扩展前完成阶段门禁。
- [ ] 前端基于冻结契约开发，不复制 DTO、不伪造真实数据。
- [ ] 每个角色每天只记录阻断项、契约变化和新增风险，不写流水账。
- [ ] 中段检查：比较实际进度与范围，发现明显超支或效果不达标时触发重新选型。
- [ ] 联调前：前后端各自通过相关类型检查和具体测试。
- [ ] 联调：使用同一候选版本和真实接口，不接受只看 fixture 的完成结论。
- [ ] 验收：总架构师保存自动化、人工、安全、性能和回退证据。
- [ ] 收口：阻断问题清零，有条件项均指定负责人和期限。
- [ ] 合并：短期分支合入共同基线，下一里程碑从最新基线创建分支。
- [ ] 决策：产品负责人明确勾选“允许进入下一阶段”或“退回修复”。

## H. 发生偏差时怎么处理

- [ ] DTO 需要变化：暂停相关前后端实现，由后端提交变更，总架构师重新批准，前端更新 fixture 后继续。
- [ ] 前端等待接口：继续页面骨架、状态、测试和适配层，不在组件内发明字段。
- [ ] 后端等待页面反馈：继续契约测试、fixture、错误语义和可观察性，不静默改变 API。
- [ ] 自研效果不达标或明显超时：暂停扩展，重新比较成熟方案与剩余自研成本。
- [ ] 出现安全、跨租户、Secret 泄漏或版本漂移：立即停止里程碑，按 P0 处理。
- [ ] 出现范围新增：产品负责人决定替换当前范围、延后到下一里程碑或单独建规格。
- [ ] 验收不通过：保留原候选证据，退回负责人修复，使用新提交重新执行受影响场景。
- [ ] 分支长期未合并：拆成更小的可验证提交，优先合并契约和独立能力，避免继续扩大差异。
