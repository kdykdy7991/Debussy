# 功能开发规格

本目录存放“开发人员拿到后可以开始实施”的功能规格。它是开发期间的工作入口，不是长期产品真相源。

## 什么时候创建

满足以下任一条件时，应先写开发规格：

- 修改两个以上 package 或系统平面；
- 新增协议、数据库迁移、权限或持久化状态；
- UI、服务端和运行时需要共同实现同一流程；
- 验收条件无法仅靠 issue 标题说清楚；
- 多名开发者需要并行协作。
- 需要新增第三方依赖、重复实现通用能力，或在自研与现有方案之间进行选择。

小型、局部且实现明确的修改可以直接通过 issue 或任务描述开发，不强制创建文档。

## 文件规则

- 每项功能使用一个文件，名称固定为“功能名 + 创建日期”：`feature-name-YYYY-MM-DD.md`。
- 功能名使用简短、可识别的英文 kebab-case；日期使用四位年份的 ISO 格式，不使用文档更新时间替换创建日期。
- 示例：`agent-state-mapping-2026-08-21.md`、`chat-file-upload-2026-08-21.md`。
- 复制 [`TEMPLATE.md`](./TEMPLATE.md) 后填写。
- 文档状态只能是：`草案`、`可开发`、`实施中`、`已完成`。
- 只有状态为 `可开发` 或 `实施中` 的文档可以作为编码依据。
- 涉及非简单通用能力时，只有完成“现有方案调研与选型”后才能评审为 `可开发`。
- 未确认的产品问题不能由开发规格自行决定，应先回到 `docs/product/` 确认。
- 同一功能在同一天只有一份实施文档；后续修改继续更新原文件，不因更新时间重复创建。

## 生命周期

```text
产品规则确认
→ 编写开发规格
→ 调研仓库能力与成熟外部方案
→ 最小原型验证和方案选择
→ 评审为“可开发”
→ 实施与验证
→ 稳定结论回写官方文档
→ 删除开发规格
```

已完成规格不长期堆积在本目录。需要追溯时使用 Git 历史、提交记录和测试。

## 方案选型门禁

方案调研的深度与任务成本成比例，但必须先于正式编码：

1. 检查仓库已有组件、依赖、历史实现和上游 runtime 能力。
2. 检索目标生态中维护活跃、许可证兼容的成熟方案。
3. 用真实核心场景做最小原型，不以 README 或演示效果代替验证。
4. 比较满足程度、接入成本、长期维护、包体/性能、安全、许可和退出成本。
5. 明确选择复用、封装、二次开发或自研，并把理由写入开发规格。

实施中出现以下任一情况时，暂停扩展代码并重新执行选型：

- 核心效果连续无法达到验收标准；
- 实际工作量明显超过规格中的预期；
- 为通用能力持续增加补丁、状态分支或专用测试；
- 发现新的成熟候选方案可能直接覆盖核心需求；
- 当前实现的维护、性能或兼容风险开始高于替换成本。

重新评估时比较“继续自研的剩余成本”与“现在迁移的成本”，不把已经投入的时间作为继续自研的理由。

默认优先顺序为：复用仓库能力 → 接入并隔离成熟依赖 → 在明确缺口上扩展 → 最后选择完整自研。该顺序不是强制采用第三方库；候选方案不满足核心要求、风险不可接受或维护成本更高时，应记录证据后自研。

正式接入第三方依赖前仍须按仓库依赖安全规则审查精确版本、锁文件、生命周期脚本、许可证、浏览器/运行时兼容性和替换边界。

本规则不要求追溯重写所有已完成规格。正在实施且仍面临关键方案选择的功能应补齐本节；已经稳定完成的功能只在发生替换、扩展或重大维护问题时重新评估。
